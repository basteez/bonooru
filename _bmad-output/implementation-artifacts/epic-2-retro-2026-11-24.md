Key measured numbers:

- The Switch 2 polls the wired Pro Controller every 8000 µs (median and p95), whatever `bInterval` says (Story 2.3 H.15, Story 2.5 H.18).
- The scheduler applies events at most 14 µs late (H.18).
- Core 0 hang to reset: 20.0 ms (H.2a, 5 runs). Core 1 hang to reset: 80.0 ms (H.2b).
- Audio (H.19): 62/62 notes audible and at the right pitch. IOI p95 18.14 ms (1.088 frames), EXPLAINED: firmware bound 8.01 ms, game floor 12.94 ms, residual +2.92 ms within the 4 ms allowance.
- Core 1 stack high-water mark: 1244 B (H.18) and 1228 B (worst-case soak), under the 1536 B limit. `PICO_CORE1_STACK_SIZE` stays 0x800.
- Link watchdog: `LINK_LOST` about 81 ms after the last heartbeat (H.9, 3 runs).

## 2. What went well

- **Hands-on measurement at the bench** (the owner's main point). Measuring with the multimeter and the microphone, and reading the board's own data, caught things host tests could not:
  - H.15 showed the console repeating a refused pairing request (`01`) forever. This led to D34 (answer `01` and `21` like a real controller, from the S12 capture).
  - H.7 measured GP0 at 0 V with only the controller powered and at 3.28 V with the peer idling high. This closed the controller side of C5.
  - H.2b compared host and board (75.9 ms against 80.0 ms). This exposed the RP2040 watchdog TIME-field read (the SDK header says it returns the last value set, not the remaining time) behind the bogus 270 ms.
  - H.19 turned AC3 into a number with an explanation instead of an argument.
- **The story cycle held up.** Each story went story lead → create-story → dev-story → CI → code review → PR. Decisions were made autonomously and recorded as numbered D-entries the owner could overrule. Every new gate and test was shown failing once ("red proof") before it was trusted.
- **Clean-room discipline held.** P2 values came from public captures and notes (S1 to S13). GPL code (nxbt, GP2040-CE, joycontrol code) was not read.
- **Bugs found at the bench went back into host tests.** Examples: F.20 reproduces the H.5 probe failure, F.23 models the bridge and the scripted owner, and the S12 init replay is a host test.

## 3. Challenges

### 3.1 Bench failures: five of six were the test tools, not the firmware

| Attempt | Story | Cause | Fix |
|---|---|---|---|
| H.15 attempt 1 | 2.3 | **firmware**: pairing request `01` refused, so the console retried forever | D34 |
| H.15 attempt 2 | 2.3 | **firmware by design**: inputs never reached the report (published state was NEUTRAL in every build, D12), so no icon | D35 (debug builds report the published state) |
| H.5 first run | 2.6 | **probe**: soak-wide 30 s deadline, and unpaced writes overflowing the 2wiCC_Comms ring | D30, D33 |
| H.12 unarmed | 2.7 | **probe**: single-shot sends after a bouncing replug | D40, D41 |
| H.12 armed ×2 | 2.7 | **probe**: took the replug bounce for the next round's unplug | D42 |
| H.2a attempt 1 | 2.5 | **tool**: host-side criterion (macOS removal latency is about 113 ms, not the assumed 25 ms) and HELLO sent before the fresh-boot read | D31 to D33 |
| H.2b attempt 1 | 2.5 | **firmware measurement**: stall-to-reset read from the watchdog TIME field, which the RP2040 does not report as remaining time | D34 (computed from the last feed) |

The firmware behaved as specified in every failed H.5 and H.12 run. The firmware goes through create-story, CI and code review before the bench. The probes and the H-row commands were reviewed only after they had failed at the bench, so each tool bug cost an extra bench round.

### 3.2 Console and host surprises (now documented)

- **macOS "Allow accessories to connect".** On "Ask", a pending prompt left the controller suspended and gone from the USB tree, and the first H.11 attempt failed. The bench setting is now "Always", and `p2_probe.py` hints at it.
- **The Switch 2 shows a wired controller only after its first input.** Before that there is no icon and no Controllers-menu entry, even though a player slot is assigned. The H.15 criterion became "first input acted on".
- **OoT's controller connection screen.** D-pad down ×3 (the first input) brings it up in ocarina free play. `selfplay` now waits for the owner to dismiss it (Story 2.5 D37).
- **Sleep is a power cycle.** The Switch 2 cuts USB power in sleep, so the controller boots again on wake (H.16).
- **Soak on the timeline build.** That build loads its 158-event table at every HELLO, so every soak `QUEUE_EVENT` got `NAK BAD_STATE`. The soak moved to a new preset `fw-debug-o3`, and `soak` now refuses a loaded queue (D38).
- **The Mac completes the P2 handshake by itself** (`report_period_us` 2000). `selfplay` and `p2check` now refuse a host that is not the console (D36).

### 3.3 Hardware handling (owner's account, not in the story files)

- 2026-11-23: the controller board would not enter BOOTSEL. The likely cause was the USB cable.

### 3.4 Smaller observations

- The published-state handoff needed two iterations. Story 2.3 fixed a NEUTRAL blip with "publish on change, keep the last good copy". Story 2.5 replaced that with a generation-counted seqlock (D22) and a NEUTRAL fallback after 3 tries; H.18 saw no fallback.
- Bench numbers were recorded wrong once (Story 2.7 H.12, caught by review round 2 against the logs).

## 5. Unfixed findings and open issues

Open issues, both deferred by the owner until after Epic 3:

- **#20**: the purity gates miss `exit`, `abort`, `fopen`, `strdup`, `alloca`, inline `asm` and raw register addresses (Story 2.6 M-5, also Story 2.3 finding (a) and the Story 2.5 review). Low risk.
- **#25**: P2 reply-queue overflows are counted but not shown in the debug STATUS (Story 2.3 finding (c)). Low priority.

Open issues from Epic 1, untouched by Epic 2: **#12** (a held note is cut on roughly every 7th sounded note in free play) and **#13** (possible double attacks on X).

Accepted MINOR findings without an issue:

- Story 2.3 (b): the libFuzzer target `fuzz_p2` does not run in CI (Apple clang has no libFuzzer); the deterministic F.28 covers CI.
- Story 2.4 M7: `now_us` is a u32 on the wire and wraps after about 71 minutes of one piece.
- Story 2.4 M6: `ready()` is sampled only at `START` / `SET_STATE`; losing readiness mid-PLAYING relies on the USB abort causes. Story 2.6 wired them: red check (l) shows a bus reset aborts the core with `EVENT USB_SUSPENDED`.
- Story 2.6 accepted note: after a rewind, a late ACK can briefly under-count the bytes in flight in the probe (window under about 21 ms).
- Story 2.7 (a) to (i): accepted edge cases in the watchdog, the test fixture and the probe.
- Story 2.5: the loader's pass before `START` is not timed by `loop_max_us` (bounded by the 20 ms liveness rule), plus five minors of the final re-review. Each can only cause a false FAIL, never a false PASS.

### Significant discoveries: epic text updated in this retrospective

Epic 2 showed that two Epic 3 acceptance criteria no longer matched the console. Both were corrected in `_bmad-output/planning-artifacts/epics.md`, with the owner's approval:

1. **Story 3.4**: new AC. Before `START`, `ocb-dev` sends D-pad down ×3 in DIRECT (never A), prompts the owner to dismiss OoT's controller connection screen and reopen the ocarina, keeps the link alive with `PING`, and starts on Enter (Story 2.3 H.15, Story 2.5 D37). The soak AC now names a controller build without the built-in timeline (Story 2.5 D38).
2. **Story 3.5 (H.3)**: "back to 0 within 150 ms on sleep" is replaced. On sleep the console cuts USB power (Story 2.3 H.16): the controller powers off, STATUS stops, and after wake the session reports "controller rebooted" and `console_ready` returns to 1 after the new handshake. The 150 ms rule stays for Wired Communication OFF.

No architectural assumption was proven wrong. The plan for Epic 3 stands with these two corrections.

The hardware-in-the-loop line of the `epics.md` requirements inventory (H.3) was aligned with the same wording.

## 9. Key takeaways

1. Measuring on the real console and with real instruments found what host tests could not: the pairing loop, the watchdog TIME field, sleep as a power cycle, and the first-input rule.
2. The bench tools are code too. They need review and a dry run before the bench, not after a failure.
3. Console behaviour discovered at the bench must flow back into the next epics' acceptance criteria. Two Epic 3 ACs were corrected in this retrospective.
