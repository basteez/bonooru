# Story 4.6: Firmware version check and gating

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the owner,
I want the app to refuse to drive boards whose protocol doesn't match,
so that an old firmware can never misread my inputs (FR-10).

Origin: `epics.md` Epic 4, Story 4.6 (FR-10 detection + gating, UX-DR13 in its Epic 4 form: OK-only dialog, no wizard link; UX-DR38 "a required update pending" gamepad hint; UX-DR62 no stacked modals; AD-7, AD-13, AD-16). It builds on Story 4.3 (`ui::modal::Modals`, `ModalSpec`, `take_outcome`, the Esc contract, `widgets::text_node_colored`), 4.4 (`ocb-services` worker, `LinkSnapshot`, `WorkerEvent::Link(LinkEvent::RequiredUpdate)`, the `version` log lines) and 4.5 (`ocb_app::leds`: the LED rows P5/C2 already show "Bridge v<x>" ok and "Controller v<y>" warning, AccessKit "… – update required"; `LinkSnapshot.required_update` and `connected_us`; the UI clock; the `led` log pattern). It carries the Epic 3 retro rules E3-A1 (AC → measurement table below), E3-A2 (no bench tool is new or changed: stated, so no verdict-branch red proofs are owed; every new host check still gets a red proof) and E3-A3 (no rig block: no bench, see "Bench decision").

**Scope: host code + docs + a short owner eye check in the gallery. No firmware change, no wire change, no hardware bench.** In scope: a pure gate model (`ocb_app::gating`, no egui) saying whether the gamepad and Play are blocked by a required update; the "Firmware update needed" modal (OK only) requested once per mismatching connection; the inline hint in the gamepad panel; `gate` and `dialog` lines in `bonooru.log`; a worker test proving nothing is written to an incompatible controller; the LED required-update tooltip made neutral (a board can be newer than the app); docs (`EXPERIENCE.md`, `DESIGN.md`, `epics.md`, `docs/test-plan.md`, `app/README.md`). Out of scope: the gamepad itself and its other block reasons (no bridge, link down, Switch not ready: Story 4.8), the Play buttons and their tooltip (Epic 6), STOP and Esc-as-STOP (Story 4.7), "Update now" / "Not now" / wizard / "Set up / Reflash…" / recommended-update banner (Epic 8), re-probing an incompatible controller without a reconnect (Open questions 1), Windows and Linux runs (issue #43; nothing OS-specific here).

## Acceptance Criteria

Numbers marked *(story)* are set by this story; every number is measured as listed in the AC → measurement table.

1. **Required update detected from INFO (FR-10, AD-7).** When the worker's snapshot has `required_update = Some(info)` (the session got INFO with `proto_ver` ≠ `ocb_core::protocol::consts::PROTO_VERSION` and is `Phase::Incompatible`), the gate model reports `Block::FirmwareUpdate { controller_proto, app_proto }` for both the gamepad and Play. The decision uses `required_update` only: never `info` (it is `None` in `Incompatible`) and never `status` (a mismatching controller's STATUS is decoded with this app's layout and is not trusted, AD-7: only INFO byte 0 is frozen). With `required_update = None` the gate has no firmware block (4.8 adds the other reasons).
2. **Blocking "Firmware update needed" modal, OK only (UX-DR13, Epic 4 form).** On the first frame whose snapshot carries a required update for a connection the app has not yet shown it for, the app requests one modal through the shared `Modals` host: title "Firmware update needed"; one centred body text (`ModalBody::Text`) = Dev Notes › Copy "Modal body" (both boards, the `.uf2` files of this app version, hold BOOT, plug in, drag onto the RPI-RP2 drive); a single primary button "OK"; no secondary button, no checkbox, no wizard link; outer width 440 pt *(story; mock `key-dialogs.html` `.modal{width:440px}`, = `components.modal-dialog.min-width`)*. It is drawn in the same frame the snapshot is drained (the request comes before `Modals::show`). "OK" (click or Enter) and Esc both close it (`ModalOutcome::Primary` / `Dismissed`); either outcome is read back with `Modals::take_outcome` and logged; neither changes the gate.
3. **Shown once per connection, no nagging.** "Connection" = one INFO of one session, identified by `LinkSnapshot.connected_us` (worker clock, new on every open). After the modal for a connection was requested, later snapshots of the same connection (same `connected_us`) never request it again, also after OK/Esc and for any length of time (host test: 10 s of fake time, 0 further requests). While the modal is open a second request is ignored by `Modals` (same id; UX-DR62: no stacked modals).
4. **Reshown on reconnect and on relaunch (UX-DR13, epic AC 3).** When the bridge is unplugged and plugged back (port lost → reopened → new INFO, new `connected_us`) and the mismatch persists, the modal is requested again. A newly started app (new `App`) whose first mismatching snapshot arrives requests it again. When a reconnect brings a matching controller (`Connected`), no modal is requested and the firmware block is gone.
5. **Gamepad off with the inline hint while the block lasts (UX-DR13, UX-DR38).** While the gate has `Block::FirmwareUpdate`, the gamepad panel shows the `inline-hint` "The gamepad is off until both boards are updated." (`typography.small` 12.5 pt Nunito Sans 400, `text-muted`), inside the gamepad region, 10 pt from its left, right and top edges *(story; mock `.right{padding:10px}`; Story 4.8 moves it under the pad)*, wrapped to the region width minus 20 pt, as one `Role::Label` AccessKit node named with the text, not focusable (not in the Tab ring). Without the block no hint text and no hint node are drawn. The hint is visible behind the modal (scrim over it) and after OK/Esc.
6. **LEDs keep showing the boards' current versions (UX-DR13).** With the modal open and after it closes, the three LEDs are those of the Story 4.5 rows P5/C2/S-unknown: PC↔Bridge ok "Bridge v<bridge_ver>", Bridge↔Controller warning "Controller v<fw_ver>" (AccessKit "Controller v<fw_ver> – update required"), Switch unknown; the modal does not change, hide or reorder them. The C2 tooltip first line becomes "This firmware doesn't match this app." (was "…is too old for this app.", wrong when the board is newer; Dev Notes › D6); its fix line is unchanged.
7. **Nothing is sent to an incompatible controller (defence in depth; AD-7, AD-16).** After `RequiredUpdate` the worker writes no further byte to that port while the session stays `Incompatible` (host test: `port_writes` for the port unchanged over 10 s of fake time after the INFO, with the fake controller sending STATUS every 50 ms), and a command attempted on the session (`session_mut().set_state(NEUTRAL)` with feature `sim`) returns `Err(CommandError::NotConnected)` and writes nothing. (No UI command reaches the worker yet: `WorkerCommand` has only `Shutdown`; Story 4.8 adds `SetState` and must keep this.)
8. **Recommended update: logged, nothing blocked (epic AC 2, AD-13).** INFO with the app's `PROTO_VERSION` and `fw_ver` or `bridge_ver` (non-zero) ≠ the app version → the worker's existing line `version recommended update fw=… bridge=… app=… fw_differs=… bridge_differs=…` is written (Story 4.4, unchanged), the gate has no block, no modal is requested, no hint is drawn, the LEDs are the normal P4/C-ok rows. No banner (Epic 8).
9. **Gate and dialog changes are logged.** Each change of the gate writes one `gate` line and each request and close of the firmware modal writes one `dialog` line to `bonooru.log` through the app's `LogHandle` (non-blocking, AD-16), in the exact formats of Dev Notes › Log lines. No line while nothing changes.
10. **The model stays pure and the UI never waits.** `app/gui/src/gating.rs` names no GUI crate (source check, self-tested like G.14's); the trigger state lives in plain data; the app reads only the latest snapshot (no new channel, no blocking call; G.13 scans keep passing).
11. **No regressions, CI green.** `cargo fmt --all --check`, `cargo clippy --locked --workspace --all-targets -- -D warnings`, `cargo test --locked --workspace`, `cargo deny --locked check licenses bans`, the G.8 scripts, the smoke run (`worker=` ≥ 1) and the "ocb-sim never ships" step stay green on ubuntu, windows and macos. G.1, G.10–G.16, C.23–C.26 keep passing (G.12 and G.14 updated only where the dialog body or the C2 tooltip text changes, with the reason in the Debug Log). Every new check has a red proof in the Debug Log.
12. **Docs and owner eye check.** `EXPERIENCE.md`, `DESIGN.md`, `epics.md`, `docs/test-plan.md` (C.27, G.17, G.18; no H row, with the reason) and `app/README.md` updated as in Task 7. The owner looks at the dialog and the hint in the gallery (`bonooru --gallery`, Task 9) and the answers are recorded. M5 stays TODO (Stories 4.7–4.9).

## Dev Notes

### Scope in one paragraph

The protocol gate already exists below the UI: on INFO with another `proto_ver` the `ocb-core` session goes `Incompatible`, stops sending and refuses every command, and the controller itself, given a mismatched HELLO, closes its session and forces neutral (`docs/link-protocol.md` "Rules the controller link applies (Story 2.6)"). The worker keeps that INFO in `LinkSnapshot.required_update` and logs `version required update …`; the Story 4.5 LEDs already show the versions with a warning. This story adds what the user sees and what later stories read: a pure gate (`gating::evaluate`) that Story 4.8 (gamepad) and Epic 6 (Play) consult, an OK-only modal requested once per mismatching connection, the inline hint in the gamepad panel, and two log lines; plus one worker test proving the wire stays silent.

### Decisions taken at story creation (change only with a reason in the Debug Log; the owner can overrule any)

- **D1. Trigger on the snapshot, keyed by `connected_us`, not on the event ring.** `WorkerEvent::Link(LinkEvent::RequiredUpdate)` exists, but the UI keeps only the last 64 events and the worker drops events when its queue (1024) is full; the snapshot is always the latest. `connected_us` is set by the worker for the INFO that made the session `Incompatible` and is new for every open, so "new `connected_us` with `required_update`" = a new mismatching connection; a reconnect is recognised even if the UI never saw the `None` in between (snapshot channel of capacity 1).
- **D2. The gate model lives in `ocb-app` (`src/gating.rs`), pure, beside `leds.rs`.** Same reasons as Story 4.5 D1: UI policy over `LinkSnapshot`, tested as plain data, no egui (source check). The modal spec (egui types) lives in `ui/firmware.rs`; the copy strings live in `gating.rs` (one place).
- **D3. OK only, OK = Esc, no gate change on close.** Epic 4 has no wizard (no forward links). "OK" plays the role of the later "Not now"; Esc closes the topmost dialog by the Story 4.3 contract (and is STOP for Story 4.7). Closing never lifts the block: only a new connection with a matching INFO does.
- **D4. Once per connection; no re-show while the mismatch persists on the same connection.** UX-DR13 asks for "next launch or reconnect"; repeating it on a timer would nag and steal focus from the main screen. The hint and the LED warning stay visible meanwhile.
- **D5. No re-probe while `Incompatible` (Open questions 1).** The session sends nothing after the mismatched INFO (pinned by `app/sim/tests/open.rs` and, new, C.27). Recovery comes with a reconnect of the bridge (reflashing the bridge unplugs it anyway) or a relaunch. Re-HELLOing an incompatible controller would change the Story 3.3 app-side rule ("another `proto_ver` stops the HELLOs") and add writes to a bridge that may have lost its controller (issue #45: a macOS close can hang when the bridge stops taking bytes); left to Epic 8's post-flash verification unless the owner decides otherwise.
- **D6. LED C2 tooltip made neutral.** A mismatch can be an older or a newer board (`controller_proto` > `app_proto` when the app is the old one); "too old" would be false then. The modal body is worded the same way.
- **D7. The hint sits at the top of the empty gamepad panel until Story 4.8.** The mock puts it under the pad (`.ihint{margin-top:8px}` after the legend); with no pad yet, it starts at the panel padding (10 pt). Story 4.8 moves it under the pad and keeps `widgets::inline_hint`.
- **D8. `gate` and `dialog` lines, no new bench tool.** They give the host tests (and any later bench) one place to read gate decisions from, in the same log and `+ms` stamps as the `led` and worker lines (Story 4.5 D11 pattern).
- **D9. No hardware bench.** See "Bench decision".
