# Story 4.5: Status strip with three live LEDs

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the owner,
I want three always-visible LEDs for PC↔bridge, bridge↔controller and controller↔Switch,
so that I can see at a glance what is ready while my eyes are on the console (FR-23).

Origin: `epics.md` Epic 4, Story 4.5 (FR-23, NFR-06, UX-DR8, UX-DR9, UX-DR10, UX-DR11, UX-DR62, UX-DR65; the Story 4.2 accessibility line: each LED a `Role::Status` node; the Story 4.4 forward note on OQ-5/OQ-6). It builds on Story 4.1 (theme tokens, fonts, regions, smoke run), 4.2 (AccessKit level "basic"), 4.3 (`ui::paint`, `ui::symbols`, `ui::widgets`, focus ring, kittest conventions) and 4.4 (`ocb-services` worker, `LinkSnapshot`, `WorkerEvent`, `App::worker_health()`, the `bonooru.log` file, the H.28/H.31 macOS data). It carries the Epic 3 retro rules E3-A1 (AC → measurement), E3-A2 (red proof per verdict branch of a bench instrument), E3-A3 (bench start checklist) and the OQ-3 (150 ms STATUS staleness) and OQ-4 (100 ms `console_ready` rule, firmware side, unchanged) decisions.

**Scope: host code + a macOS bench + an owner eye check.** No firmware change, no wire change. In scope: the pure LED model, the status strip drawing, tooltips, keyboard focus, AccessKit nodes, the LED transition lines in `bonooru.log` (the bench's measuring instrument), four small additions to `LinkSnapshot`, the OQ-5/OQ-6 decisions written into `EXPERIENCE.md` and `epics.md`. Out of scope: the version modal and Play/gamepad gating (Story 4.6), STOP and the bottom bar (4.7), the gamepad (4.8/4.9), the Settings gear (Epic 5: hidden here), "Set up / Reflash…", LED click → wizard, the update banner (Epic 8: none of them drawn here), Windows and Linux benches (issue #43, sprint action S4.4-A1).

## Acceptance Criteria

Numbers marked *(story)* are set by this story; every number is measured as listed in the AC → measurement table.

1. **Strip layout (UX-DR8).** The status strip (the existing 44 pt region, `panel-raised` with its `rim-soft` hairline, unchanged) shows, left to right: the brand "Bonooru" in `typography.brand` (Cormorant Garamond 23/700) in `parchment`, then the three Status LEDs in the order PC↔Bridge, Bridge↔Controller, Controller↔Switch, 20 pt apart. Left inner padding 16 pt (`spacing.4`), brand-to-first-LED gap 28 pt *(story; mock `key-empty-state.html` `.status{gap:28px}`)*, symbol-to-label gap 7 pt *(story; mock `.led{gap:7px}`)*, each LED vertically centred in the strip. The gear and the "Set up / Reflash…" link are not drawn (no widget, no AccessKit node) until Epic 5 / Epic 8. At the minimum window width (1024 pt) and with the longest label of each LED, all three LEDs fit inside the strip without clipping or overlap.
2. **Four LED states, never colour alone (UX-DR9, UX-DR62).** Each LED is an 11 pt symbol + a label in `typography.body-strong` (`text` colour) + an optional detail in `body` / `text-muted`: `ok` = filled dot in `status-ok` with an 8 px CSS-blur glow of the same hue (`paint::paint_glow`, `theme::glow::STATUS_LED`); `warning` = filled triangle in `status-warning` (convex fill via `paint::fill_convex`); `error` = cross (two strokes, round caps) in `status-error`; `unknown` = hollow ring in `status-unknown`, label only (no detail). Labels and details come from Dev Notes › LED decision table and › Copy (Voice table strings: "Bridge v0.3.0", "Switch – not ready", "Controller – not answering", "Bridge – not found", "Bridge – found"). Strokes go through `paint::stroke` (1 physical px floor).
3. **Tooltip on hover and on keyboard focus (UX-DR9, `EXPERIENCE.md` Banned: hover-only actions).** Each LED is focusable (`Sense::focusable_noninteractive()`, not clickable), paints the shared focus ring (`paint::paint_focus_ring`, radius `rounded.sm`) when focused, and is reached with Tab before any other control (the status region is first in the tab order). Its tooltip (`components.tooltip`: `panel-raised`, 1 pt `rim-soft`, `rounded.md`) shows the detail line, then the fix on its own line when there is one; it opens on hover (egui's normal delay) and immediately while the LED has keyboard focus. Exactly one tooltip is shown for a LED that is both hovered and focused.
4. **The LEDs follow the Hardware & Protocol Coupling table (UX-DR10, UX-DR11, UX-DR65).** A pure function maps (latest `LinkSnapshot`, time since it was received, `WorkerHealth`) to the three LEDs exactly as Dev Notes › LED decision table says. In short: no `2E8A:000A` port → PC↔Bridge error "Bridge – not found"; only a foreign product string → PC↔Bridge warning, the tooltip naming the board; `Ours` port open, no INFO → PC↔Bridge ok "Bridge – found"; INFO → PC↔Bridge ok "Bridge v<bridge_ver>" and Bridge↔Controller ok "Controller v<fw_ver>"; no INFO within the INFO grace → Bridge↔Controller error "Controller – not answering", Switch unknown; `link_ok` 0 or a `NAK NO_LINK` newer than the last STATUS → Bridge↔Controller error; `console_ready` 0 or a `NAK NOT_READY` newer than the last STATUS → Switch warning "Switch – not ready", whose tooltip adds "Undock the Switch." when STATUS `last_event` is `USB_SUSPENDED`; a mid-session `NAK VERSION` (controller rebooted, the session HELLOs again) → Bridge↔Controller and Switch unknown until INFO or the INFO grace ends; port vanished → PC↔Bridge error; Linux permission denied → PC↔Bridge error with the exact Story 4.4 message in the tooltip; port held by another program → PC↔Bridge warning; protocol mismatch (`RequiredUpdate`) → PC↔Bridge ok "Bridge v<x>", Bridge↔Controller warning "Controller v<y>" with an update tooltip, Switch unknown (Story 4.6 adds the modal and the gating).
5. **Start unknown, resolve within about 1 s (UX-DR10).** Before the first snapshot all three LEDs are `unknown`. With both boards plugged and the controller on a ready Switch, the three LEDs reach their final state within 1000 ms *(story; epic: "about 1 s")* of the app's `start` log line.
6. **STATUS staleness 150 ms (OQ-3, Story 3.5).** With a session `Connected`, when the age of the last STATUS (its receive time on the worker clock, or the INFO time if no STATUS came yet, plus the time since the UI received that snapshot) is greater than 150 000 µs, Bridge↔Controller shows error "Controller – not answering" and Switch shows unknown (Dev Notes › D3); at exactly 150 000 µs the STATUS is still fresh. The UI asks egui for a repaint at the next staleness or grace deadline (`Context::request_repaint_after`), so the change is drawn without a new snapshot. On the bench the logged `status_age_us` of that change is > 150 000 and ≤ 250 000 µs *(story)*. *(amended 2026-11-27 after code review, coordinator decision)*
7. **INFO grace 500 ms *(story)*.** Bridge↔Controller and Switch stay `unknown` while a session is `Opening` and less than 500 000 µs have passed since that session opened (a port open, or a re-open after a controller reboot); at 500 000 µs + 1 µs with no INFO, Bridge↔Controller is error "Controller – not answering" and Switch unknown. On the bench the logged `session_age_us` of that change is > 500 000 and ≤ 700 000 µs *(story)*. *(amended 2026-11-27 after code review, coordinator decision)*
8. **A dead or stuck worker never shows a frozen "connected" (Story 4.4 review).** `WorkerHealth::Stalled`, `Ended` or `NotStarted` → all three LEDs `unknown`, each tooltip explaining it (Dev Notes › Copy). The change is drawn without user input: a worker that ends wakes the UI, and the UI asks for a frame at the 3 s stall deadline. *(amended 2026-11-27 after code review, coordinator decision)*
9. **OQ-5 and OQ-6 decided now on macOS data, provisional parts named (`epics.md` OQ-5/OQ-6 = `EXPERIENCE.md` Open Questions items 4/5).** OQ-6: "Bridge – found" (ok, no version) for an `Ours` bridge with no INFO, decided on the macOS bench data (H.28 `class=ours` before INFO; H.31 the bridge alone accepts HELLO with `hello_dropped=0`). OQ-5: an `Unconfirmed` port (Windows always; any OS with no product string) with no INFO shows PC↔Bridge `unknown` "Bridge" with an explaining tooltip, Bridge↔Controller error after the INFO grace, Switch unknown; as soon as INFO arrives it is shown as ours with versions. Both are written into `EXPERIENCE.md` (Open Questions items 4 and 5 resolved, State Patterns rows "Bridge only, no controller" and "Windows, no product string" updated, Voice table) and `epics.md` (OQ-5, OQ-6 RESOLVED), each with what stays provisional until issue #43 (Dev Notes › OQ-5/OQ-6 decision).
10. **Nothing implies online features (NFR-06, AD-21).** No LED label, detail, tooltip or AccessKit text contains "online", "offline", "internet", "cloud", "network", "account", "sync", "update check", "linked to game" or "free play" (case-insensitive), and no strip element is a network icon. The `cargo deny` network-crate ban stays green.
11. **Accessibility (Story 4.2: basic).** Each LED is one `Role::Status` AccessKit node whose name is its visible label + detail and says its state (e.g. "Bridge v0.3.0", "Controller – not answering"; an unknown LED is "<label> – unknown", e.g. "Switch – unknown"; a required update "<label> v<x> – update required") *(amended 2026-11-27 after code review, coordinator decision)* and whose description is the tooltip text (detail, then fix). A kittest test finds each LED by role + name in each of the four states. The brand is one `Role::Label` node "Bonooru".
12. **LED changes are logged (the bench's measuring instrument; Story 4.4 Logging convention).** Each change of an LED's state, name or reason writes one `led` line to `bonooru.log` through the app's `LogHandle` (non-blocking `try_send`, AD-16), in the exact format of Dev Notes › `led` log line, with `status_age_us` / `session_age_us` (whole µs) filled when the rule that decided it used them *(amended 2026-11-27 after code review, coordinator decision)*. No line is written while nothing changes.
13. **No regressions, CI green.** `cargo fmt --all --check`, `cargo clippy --locked --workspace --all-targets -- -D warnings`, `cargo test --locked --workspace`, `cargo deny --locked check licenses bans`, the G.8 scripts, the smoke run (`worker=` ≥ 1) and the "ocb-sim never ships" step stay green on ubuntu, windows and macos. G.1 (regions), G.10–G.13 keep passing (updated only where the strip's new content requires it). Every new check has a red proof in the Debug Log.
14. **macOS bench and owner eye check; Windows/Linux deferred.** H.33 (Dev Notes › H.33) passes on macOS with the release `bonooru`, after the instrument review and the dry run (Tasks 11–12); the owner's eye check of the strip (Task 14) is recorded. The Windows and Linux rows of H.33 are listed in `docs/test-plan.md` as "deferred: owner has no Windows/Linux machine yet (2026-11-27); issue #43" and added to issue #43's scope note in the Debug Log. M5 stays TODO (Stories 4.6–4.9).

## Dev Notes

### Scope in one paragraph

Turn the Story 4.4 snapshot into three LEDs. A pure model (`ocb_app::leds`, no egui) decides each LED's state, text and tooltip from the latest `LinkSnapshot`, the time since the UI received it and the worker's health, and says when a timed rule (150 ms STATUS staleness, 500 ms INFO grace) will next change something. The status strip draws it with the Story 4.3 helpers, makes each LED a focusable `Role::Status` node with a tooltip on hover and focus, and the app logs every LED change to `bonooru.log`, which is what the macOS bench reads. Four small fields join the snapshot so the model never has to reconstruct history from the event ring.

### Decisions taken at story creation (change only with a reason in the Debug Log; the owner can overrule any)

- **D1. The model lives in `ocb-app` (`src/leds.rs`), not in `ocb-services` or `ocb-core`.** It is UI policy (copy, states) over `LinkSnapshot`; `ocb-core` cannot see `LinkSnapshot`, and `ocb-probe` does not need it (no probe change in this story). Kept free of `egui` so it is tested as plain data (G.14 source check).
- **D2. Staleness is judged on the worker clock plus the UI's own elapsed time.** `LinkSnapshot.now_us` freezes between publishes: the worker publishes on each STATUS (50 ms) and on writes, but in an idle `Connected` session after STATUS stops nothing is written until the next scan (1 s). So age = `(snap.now_us − rx_us) + since_received_us`, where `since_received_us` comes from the app's UI clock (Task 2). The snapshot can sit in the bounded(1) channel for at most one frame because the worker wakes the UI on every publish (`ctx.request_repaint()` waker); that error is accepted. `request_repaint_after(next_change_in_us)` makes the staleness visible without a new snapshot.
- **D3. On staleness: Bridge↔Controller error, Switch unknown.** `epics.md` says "the affected LEDs drop to unknown" and the Epic 3 retro says "LEDs unknown"; `EXPERIENCE.md` (Hardware & Protocol Coupling "No INFO / no STATUS" row, its Gaps paragraph and State Patterns "Link lost (idle)", all updated with OQ-3 on 2026-11-26) says Bridge↔Controller `error`, Switch `unknown`. The spine is the more detailed and later source, and the affected LED for STATUS-derived data is the Switch (`console_ready`); STATUS gone means the controller is not answering, which is what "Controller – not answering" says. See Open questions 1.
- **D4. Versions shown as `v{X}.{Y}.{Z}`.** `DESIGN.md` › Status strip shows `v0.3.0`; the Voice table example says "v0.3". INFO carries three numbers and AD-14 versions are triples, so all three are shown. `bridge_ver` `[0, 0, 0]` (no heartbeat seen, or a bridge built without a `v*` tag, as today) is shown as `v0.0.0` (honest; the boards report it). See Open questions 2.
- **D5. INFO grace 500 ms.** H.29 measured INFO 4–5 ms after the open; HELLO goes every 100 ms, so 500 ms is five HELLOs without an answer. It keeps "Controller – not answering" from flashing on every connect and on a controller reboot ("briefly unknown", `EXPERIENCE.md` State Patterns "Controller rebooted"), and keeps "resolve within about 1 s" (scan at worker start + 500 ms).
- **D6. NAK NOT_READY / NO_LINK as latches until a newer STATUS.** "Treated like the flags" (UX-DR10): the NAK sets the same LED as `console_ready` 0 / `link_ok` 0 until a STATUS received after the NAK shows the flag at 1. No command in this story sends SET_STATE, so these rows are proven on the fake controller (`session_mut`, feature `sim`) and by hand-built snapshots; Story 4.8 is the first real sender.
- **D7. Protocol mismatch shown with versions, as warning on the Controller LED.** `EXPERIENCE.md` State Patterns "Required update": "LEDs show the boards' current versions". STATUS bytes after INFO byte 0 are not frozen across protocol versions (AD-7), so the Switch LED stays unknown in `Incompatible`. Story 4.6 adds the modal and gating; it may change this row with a reason.
- **D8. Busy and permission denied on the PC↔Bridge LED.** The Story 4.4 worker reports them in `last_error`; the strip is the only always-visible place on the main screen (UX-DR65: "a typed event carries the plain message with the exact command"). Permission denied → error with the exact message in the tooltip; busy → warning (another program holds it; nothing is broken).
- **D9. Gear and "Set up / Reflash…" hidden.** The epic hides the gear until Epic 5 and has no forward links to the wizard (Epic 4 notes). Both are absent, not disabled, so Tab and AccessKit never reach a dead control.
- **D10. LED click does nothing.** The click → wizard behaviour is Epic 8 `[ASSUMPTION]`; the LEDs are focusable for the tooltip only (`Sense::focusable_noninteractive()`), so Enter on a LED does nothing (no fake click).
- **D11. `led` lines in the existing log, no new bench tool.** The real app on the real rig is what H.33 checks; its LED decisions and the worker's port/version lines share one log with millisecond stamps, so every bench number comes from the log, not from the eye or a counter (Story 3.4 lesson: print every number the H-row needs). `ocb-probe` stays unchanged (no new verdict branches).
- **D12. Round robin on Windows with several Pico boards.** `session_since_us` restarts at each opened candidate, so with two `Unconfirmed` boards and no INFO the Bridge↔Controller LED alternates unknown (500 ms) / error (1.5 s) every 2 s. Accepted as a known limitation (rare: several Pico boards on Windows with no controller answering); recorded for #43, not fixed here.

### `led` log line (AC 12; the bench reads exactly this)

Kind tag `led`, text:

`<link>=<state> name="<name>" reason=<reason> status_age_us=<n|-> session_age_us=<n|->` (amended after code review: ages in whole µs, so the bench judges `> 150000` / `> 500000` directly; in ms rounded down a correct change 1 µs past the boundary read 150 / 500)

`<link>` ∈ `pc_bridge`, `bridge_controller`, `switch`; `<state>` ∈ `ok`, `warning`, `error`, `unknown`; `<name>` = the visible text (label + detail; the AccessKit name may add the state, AC 11); ages in whole µs, `-` when the rule did not use them. A line is written for each change of state, name or reason. Full line as written by the Story 4.4 log thread, e.g.:

`2026-11-28T10:15:02.123Z +842ms led bridge_controller=error name="Controller – not answering" reason=stale status_age_us=163400 session_age_us=-`

G.14 regex: `^(pc_bridge|bridge_controller|switch)=(ok|warning|error|unknown) name="[^"]+" reason=[a-z_]+ status_age_us=(\d+|-) session_age_us=(\d+|-)$`.

### Bench gotchas (from Epics 2–4)

- **macOS completes the Pro Controller handshake by itself** (Epic 2/3 retros): a controller powered from the Mac shows `console_ready` 1, so the Switch LED says "Switch – ready" with no Switch.
