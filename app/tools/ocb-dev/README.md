# ocb-dev

A dev-only bench tool (Story 3.4): it opens the bridge's serial port and streams a timeline to the controller through `ocb-core`'s link session (the same code the app will use). It is never shipped to users; FR-15 (a GUI for every user function) is about the app.

```
cargo build --release -p ocb-dev            # in app/
app/target/release/ocb-dev <port> <timeline.csv | soak | failsafe | watch>
```

- `port`: the bridge's serial port. On macOS only `/dev/cu.*` is opened (`ls /dev/cu.usbmodem*`); a `/dev/tty.*` path is refused with the `cu.` name to use.
- `timeline.csv`: a `t_us,state` file (format below). `timelines/ode-to-joy-90bpm.csv` is the Story 1.6 melody (62 notes, 158 events) from the Story 1.5 profile, generated by `firmware/tools/gen_test_timeline.py` together with the controller's built-in table, so it is the melody H.18 and H.19 measured.
- `failsafe` (Story 3.5, A.3): the same melody (embedded) round after round; the owner ends each round by unplugging the bridge or pulling a UART wire, then plugs it back. Each round is judged on the controller's own data: the first STATUS after the loss shows mode IDLE, `last_event` LINK_LOST and `abort_count` + 1, and the debug counters `watchdog_trips` + 1 (and `rx_be` + 1 for a wire). 20 rounds; needs a debug build.
- `watch` (Story 3.5, H.3): waits for the controller with no limit and logs every `console_ready` / `link_ok` edge, STATUS silences, reboots the session reports, and `START` probes sent while the console is not ready (they must get `NAK NOT_READY`). At Ctrl+C it prints the `H.3:` analysis (edges, silences, probes, STATUS interval median / p99 / max, the console's longest polling gap from the v4 debug block) and judges H.3.
- `soak`: the link soak (10 minutes, one event per millisecond, harmless states: neutral and a left-stick X of `0x84`, the last `NEUTRAL|END`). A file literally named like a keyword is passed as `./soak`, `./failsafe`, `./watch`.

Every run ends with a `SUMMARY:` line (events queued, `PLAYBACK_DONE`, frames sent, resends, rewinds, NAKs by reason, debug counters first and last when present) and the verdict.

Exit codes: `0` PASS, `1` FAIL (the last line says why), `2` usage or file error (nothing was opened), `130` Ctrl+C.

## What a run does

1. Opens the port at 460800 8N1 with DTR asserted, opens the session (a lone `0x00`, HELLO every 100 ms until INFO) and prints INFO (`fw_ver`, `bridge_ver`, `queue_cap`, `report_period_us` and which host that suggests: 8000 µs the console, 2000 µs a computer).
2. Waits up to 120 s for STATUS `link_ok` 1 (the bridge's heartbeat) and `console_ready` 1, held for 2 s.
3. Melody only: presses D-pad down 3 times in DIRECT (150 ms each, 300 ms apart; never A), the first input the Switch 2 needs before it shows a wired controller; then asks the owner to dismiss OoT's controller connection screen with the Joy-Con, reopen the ocarina and press Enter. The session's PINGs keep the link alive meanwhile (up to 300 s).
4. Prefills up to INFO `queue_cap`, sends `START` with the file's `start_lead_us`, streams on credit (at most 256 events waiting in the session), waits for `PLAYBACK_DONE` and the STOP that follows.
5. Soak only: needs a debug controller build (`fw-debug`, checked before START; never `fw-debug-timeline`, whose preloaded table the tool sees in STATUS `free` and refuses before anything is sent). PASS when no transport NAK arrived during the soak and the debug counters `dropped_bytes`, `rx_err_bytes`, `rx_overflow_bytes`, `overlong_bytes`, `tx_dropped`, `watchdog_trips` did not move between the last STATUS before START and a STATUS after the final STOP.

Once connected, a controller that sends no STATUS for 1 s fails the run (unplugged, powered off or hung); `console_ready` counts only while STATUS keeps arriving.

Ctrl+C at any point after the session opened sends STOP, waits for its ACK (up to 2 s) and prints the controller's mode from a STATUS sent after the STOP (IDLE: neutral). A second Ctrl+C leaves at once without STOP: closing the port drops DTR, which aborts DIRECT (AD-5) but not PLAYING, so a piece already queued on the controller plays on; unplug the bridge to stop it (the link watchdog goes neutral within 100 ms). Any failure also sends STOP (or finishes the one in flight) before the tool exits. Plug the controller into its USB host before starting: it is powered from there, and the tool needs its INFO within 5 s.

## Timeline format

```
# start_lead_us: 500000
t_us,state
0,0000088080808000
500000,0100088080808000
...
44166667,0000088080808001
```

- `#` lines are comments; `# start_lead_us: N` is required once.
- The first other line is the header `t_us,state`.
- `t_us`: decimal digits only (µs from START), strictly increasing, below 2^31. No signs or spaces anywhere in a row.
- `state`: the 8 AD-10 wire bytes as 16 hex digits: `buttons` (u16 little-endian), `hat`, `lx`, `ly`, `rx`, `ry`, `flags`.
- The last row is `NEUTRAL|END` (`0000088080808001`), and END appears nowhere else.
- AD-9 allow-list, checked before the port opens: buttons L, R, A, X, Y only; D-pad up, down or neutral; right stick centred; no reserved flag bit.
- At most 100 000 rows.

## Tests

`cargo test -p ocb-dev` runs the dry run: the same runner against `ocb-sim`'s fake controller on a fake clock (C.13 to C.19 in `docs/test-plan.md`). Bench rows: H.24 to H.27, A.3, H.3.
